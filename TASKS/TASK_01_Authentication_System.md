# TASK 01: Authentication System

## Purpose

Implement secure user authentication including registration, login, password reset, and multi-factor authentication (MFA). Establish JWT-based session management and role-based access control foundation.

## Priority

Critical. This task blocks all other features requiring user identity.

## Dependencies

- Database schema for User and Organization entities.
- Email service configured for verification and password reset emails.

## Acceptance Criteria

1. User can register with email and password, receive verification email.
2. User can log in with verified credentials and receive JWT access and refresh tokens.
3. User can request password reset via email and complete reset flow.
4. Access tokens expire after 15 minutes, refresh tokens expire after 7 days.
5. MFA can be enabled by user, TOTP-based codes required on login when enabled.
6. Failed login attempts rate-limited: max 5 attempts per email per hour.
7. CAPTCHA displayed after 3 failed attempts.
8. Passwords validated: minimum 12 characters, uppercase, lowercase, number, special character.
9. Passwords hashed using bcrypt with cost factor 12.
10. All authentication endpoints return consistent error messages to prevent user enumeration.

## UI Description

### Registration Page

**Components:**
- Form with fields: Email, Password, Confirm Password, First Name, Last Name, Organization Name, Organization Type (dropdown: Operator or Site Owner).
- Terms of Service and Privacy Policy checkbox (required).
- Submit button labeled "Create Account".
- Link to Login page.

**Interactions:**
- Client-side validation: email format, password strength meter, password match.
- On submit: POST to /api/v1/auth/register.
- On success: Display message "Verification email sent to [email]. Please check your inbox."
- On error: Display error message above form (e.g., "Email already registered").

**Responsive:** Single-column layout on mobile, centered card on desktop.

### Login Page

**Components:**
- Form with fields: Email, Password.
- "Remember me" checkbox (extends refresh token to 30 days).
- Submit button labeled "Log In".
- Links: "Forgot password?" and "Create account".
- MFA field appears if user has MFA enabled (6-digit code input).

**Interactions:**
- On submit: POST to /api/v1/auth/login.
- On success: Store tokens, redirect to dashboard.
- On MFA required: Display MFA code field.
- On error: Display error message, increment failed attempt counter, show CAPTCHA after 3 attempts.

### Password Reset Flow

**Step 1: Request Reset**
- Form with single field: Email.
- Submit button labeled "Send Reset Link".
- On submit: POST to /api/v1/auth/password-reset.
- Display message "If email exists, reset link sent" (prevent enumeration).

**Step 2: Reset Password**
- User clicks link in email, navigated to reset page with token in URL.
- Form with fields: New Password, Confirm Password.
- Submit button labeled "Reset Password".
- On submit: POST to /api/v1/auth/password-reset/confirm with token.
- On success: Redirect to login with success message.
- On error: Display error (e.g., "Token expired or invalid").

### MFA Setup (in Settings)

**Components:**
- "Enable MFA" button.
- On click: Display QR code (generated by backend TOTP secret).
- Instructions: "Scan with authenticator app (Google Authenticator, Authy, etc.)".
- Verification field: Enter 6-digit code to confirm setup.
- Submit button labeled "Verify and Enable".

**Interactions:**
- On submit: POST to /api/v1/auth/mfa/enable with code.
- On success: Display backup codes (store securely), MFA enabled.

## API Endpoints

### POST /api/v1/auth/register

**Request Body:**
```
{
  "email": "operator@example.com",
  "password": "SecureP@ssw0rd123",
  "first_name": "John",
  "last_name": "Doe",
  "organization_name": "Drone Pros LLC",
  "organization_type": "Operator"
}
```

**Response (201 Created):**
```
{
  "user_id": "uuid",
  "email": "operator@example.com",
  "organization_id": "uuid",
  "message": "Verification email sent. Please check your inbox."
}
```

**Validation:**
- Email: Valid RFC 5322 format, unique.
- Password: Min 12 chars, complexity requirements.
- Organization name: Max 200 chars, required.

### POST /api/v1/auth/login

**Request Body:**
```
{
  "email": "operator@example.com",
  "password": "SecureP@ssw0rd123",
  "mfa_code": "123456" // optional, required if MFA enabled
}
```

**Response (200 OK):**
```
{
  "access_token": "eyJhbGc...",
  "refresh_token": "eyJhbGc...",
  "expires_in": 900, // seconds
  "user": {
    "user_id": "uuid",
    "email": "operator@example.com",
    "first_name": "John",
    "role": "OperatorAdmin",
    "organization_id": "uuid"
  }
}
```

**Errors:**
- 401: Invalid credentials or MFA code.
- 403: Email not verified.
- 429: Rate limit exceeded.

### POST /api/v1/auth/refresh

**Request Body:**
```
{
  "refresh_token": "eyJhbGc..."
}
```

**Response (200 OK):**
```
{
  "access_token": "eyJhbGc...",
  "expires_in": 900
}
```

### POST /api/v1/auth/logout

**Request Body:**
```
{
  "refresh_token": "eyJhbGc..."
}
```

**Response (200 OK):**
```
{
  "message": "Logged out successfully"
}
```

**Behavior:** Invalidate refresh token (blacklist in Redis with TTL).

### POST /api/v1/auth/password-reset

**Request Body:**
```
{
  "email": "operator@example.com"
}
```

**Response (200 OK):**
```
{
  "message": "If an account with that email exists, a password reset link has been sent."
}
```

**Behavior:** Generate token with 1-hour expiration, send email with reset link.

### POST /api/v1/auth/password-reset/confirm

**Request Body:**
```
{
  "token": "reset-token-uuid",
  "new_password": "NewSecureP@ssw0rd456"
}
```

**Response (200 OK):**
```
{
  "message": "Password reset successful. You can now log in."
}
```

**Validation:**
- Token valid and not expired.
- New password meets complexity requirements.

### POST /api/v1/auth/mfa/enable

**Request Body:**
```
{
  "code": "123456"
}
```

**Response (200 OK):**
```
{
  "message": "MFA enabled successfully",
  "backup_codes": ["code1", "code2", "..."]
}
```

**Behavior:** Generate TOTP secret, verify provided code, store secret encrypted in database.

## Caveats and Edge Cases

### User Enumeration Prevention

Do not reveal whether email exists during login or password reset. Always return generic messages like "Invalid credentials" or "If email exists, link sent."

### Token Storage

Access tokens stored in memory (React state) only, never localStorage (XSS risk). Refresh tokens stored in HttpOnly, Secure, SameSite cookies.

### Token Revocation

Implement token blacklist in Redis for logout. When user logs out, add refresh token to blacklist with TTL equal to token expiration.

### Email Deliverability

Use reputable email service with high deliverability (Postmark, SendGrid). Configure SPF, DKIM, DMARC. Monitor bounce rates. Suppress bounced email addresses.

### Concurrent Logins

Multiple active sessions allowed (user can log in from multiple devices). Each session has unique refresh token. Logout invalidates only that session's refresh token.

### Password Reset Abuse

Rate-limit password reset requests: max 3 per email per hour. Monitor for abuse patterns (mass requests to different emails from same IP).

### MFA Backup Codes

Generate 10 single-use backup codes during MFA setup. Store hashed. User can use backup code if unable to access authenticator app. Prompt user to regenerate codes after using one.

### Account Lockout

After 10 failed login attempts within 24 hours, temporarily lock account (require email verification to unlock). Notify user via email of suspicious activity.

### Session Expiration Edge Case

If user's access token expires mid-request, frontend should automatically attempt token refresh and retry failed request transparently.

### Third-Party OAuth (Optional)

If implementing Google/Microsoft OAuth, ensure same email cannot exist for both password and OAuth accounts. Link accounts or force user to merge.

### GDPR Compliance

Store minimal data during registration. User can request account deletion (anonymize data but retain financial records per legal requirements).

## Performance Considerations

### Database Queries

- Email lookup: Indexed unique constraint on email.
- User authentication: Single query by email.

### Password Hashing

Bcrypt is CPU-intensive. For high-traffic login, consider horizontal scaling or caching user credentials temporarily (risky, not recommended for MVP).

### Rate Limiting

Use Redis for fast rate-limit counters. Key format: "rate_limit:login:{email}" with TTL.

### Token Generation

Use crypto library for secure random generation. Token signing with RS256 adds minimal overhead.

## Security Checklist

- [ ] Passwords hashed with bcrypt (cost 12).
- [ ] Passwords never logged or exposed in errors.
- [ ] JWT tokens signed with RS256, private key secured.
- [ ] Refresh tokens HttpOnly, Secure, SameSite cookies.
- [ ] Rate limiting on login and registration endpoints.
- [ ] CAPTCHA after multiple failed attempts.
- [ ] Email verification required before full account access.
- [ ] MFA secret encrypted at rest.
- [ ] Password reset tokens single-use and expire in 1 hour.
- [ ] Generic error messages prevent user enumeration.
- [ ] HTTPS enforced for all authentication endpoints.
